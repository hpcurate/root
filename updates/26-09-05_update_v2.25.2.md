## What was done

### It was never a rendering artefact

`--mu` is `#4a4a4a` on a `#0e0e0e` ground. That is a contrast ratio of
**2.18:1**, under half the minimum for body text. It is the **placeholder**
colour — tokens.css has always named it that — and the title band's date line
was using it as a **label** colour, at 10px, bold, uppercase, with .16em of
letter-spacing.

Small text at 2:1 does not read as faint. It reads as **out of focus**.

That is the whole bug. It is also exactly why four fixes changed nothing: none
of them was touching the thing that was wrong.

| 2.25.1 | `black-translucent` status bar | yes | no |
| **2.25.2** | **`--mu` used as a label colour** | **yes** | **yes** |

### The fix

The band's label rows take `--tx-2` — **6.86:1** — across all nine namespaces
that have one (`do`, `log`, `plan`, `store`, `tend`, `track`, `learn`, `cal`,
`settings`).

The actions sitting in the same band followed, because they were the same colour
and equally soft in the screenshot: DO's and TEND's `sync`, LOG's date arrows
and its "today" chip, STORE's settings link.

`--mu` itself is **unchanged**. It is still `#4a4a4a` and still the placeholder
colour — that is the right value for a hint inside an empty field, which is
meant to recede and which you are about to type over. It now carries a note
saying that is all it is for, and `shell.css`'s band comment records the whole
five-release history so the next person to see a soft band does not start by
snapping pixels.

**All four earlier fixes are kept.** Each was a genuine defect found on the way
and each is worth having on its own terms. None was reverted to get here, and a
check asserts that.

### What went wrong in the diagnosis

The screenshot said it plainly on the first look and it took four releases to
read: **every soft thing in it was `--mu`** — the date line, `sync`, the day
number, the inactive tab chips — and **every crisp thing was not** — `DO.`,
`ROUTINE P1`, `chores`. That is a colour pattern, not a rasterisation pattern.

The second signal was ignored for longer than it should have been: four
independent, correct, well-reasoned fixes that each produced *literally no
change* is not four unlucky guesses, it is four pieces of evidence that the
model was wrong. "Nothing has changed" should have moved the search off
rendering entirely by the second report, not the fifth.
