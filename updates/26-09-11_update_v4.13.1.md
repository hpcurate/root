## What was done

Both faults were 4.13.0's, and both sat behind the same button.

### DO's header sync had stopped closing routines

4.13.0 repointed DO's header `sync` at the device sync. That button already had a
job — `DO.syncTodoist()`: close in Todoist the routines finished here, and tick
here the ones finished over there — and repointing it dropped that job on the
floor. The routine progress was not "not syncing"; it was **not being closed**,
because the thing that closes it was no longer being run.

The update log for 4.13.0 called this a decision made on Hugo's behalf. It was
the wrong one: "make sure that the sync button at the top of do has this
functionality now" is *and*, not *instead of*.

It now runs both, **routines first** — that order matters, because the routine
sync can tick routines on this device, and those ticks should be in the payload
the device sync sends a moment later.

- `DO.syncTodoist(quiet)` takes TEND's existing `quiet` flag and returns
  `{ pulled, pushed, failed, msg }`, so a caller with its own line to compose can
  suppress the toast and still say what happened. Called with no argument — which
  is how its own button under settings → do calls it — nothing about it changed.
- The header's line reports the routine half only when it actually moved
  something. A board with no Todoist section chosen for DO says so once, in DO's
  own panel, rather than on every sync from the header.

### An import landed where nobody could see it

The reviewed import has always ended with *"Imported N records — reload now?"*,
because every view is holding what it read at boot. `SYNC.run()` — the one-tap
path added in 4.13.0 — committed and then said nothing but a toast. Ticks from
the other device were written to storage and the screen in front of you carried
on showing what it had.

That is the second half of "not completing", and it would have made the device
sync look broken even with the routine sync back.

- One `offerReload(n)`, used by one tap; the reviewed import keeps its own
  wording.
- The automatic run **never** opens a dialog — it toasts `sync took in N —
  reload to see them`. A timer that takes the page away mid-sentence is worse
  than a stale view.

## Verification

`node test/update.mjs check --full` — **1229 harness checks, 0 failed**, syntax
over 20 files, boot smoke, and the runner's own 6 tests. Eight checks are new:

- `DO.syncTodoist` takes the quiet flag, answers its caller, and its own button
  under settings → do still calls it plainly
- one tap runs both, and the routine sync is ordered first
- an import that wrote records offers the reload
- an automatic run toasts and opens no dialog

**Not verified:** the same limit as 4.13.0 — the round trip needs two real
devices and the real Todoist API. What is checked here is that the button calls
both halves, in that order, and that a write is followed by the offer to re-read.
Whether a routine closes in Todoist is `DO.syncTodoist()`'s own business and was
covered before this update.

## Note

The desktop report from the same conversation — the SYNC box missing on desktop
while the moved-notice showed — was a stale `js/settings.js` in the browser
cache, not a fault in the build: none of root's script or stylesheet tags carry a
version and there is no service worker, so a warm desktop cache can pair new HTML
with old JS. A hard reload fixes the instance. The durable fix (a version stamp
on every asset) is **not** in this update; it was offered and is waiting on a
yes.
