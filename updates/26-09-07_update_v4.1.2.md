## What was done

### CREATE was not drawing nothing — it was not there

`js/create.js`. Each module in ROOT is `window.X = (function(){ … })()` with its
own boot sequence at the bottom of the IIFE, so **anything that throws in there
runs before the assignment** and `window.X` ends up `undefined`. There is no
partial app, no error on screen, and nothing that says so: the slide is empty,
and every `window.CREATE && CREATE.…` guard elsewhere quietly does nothing —
which is exactly why the settings panel's fields were blank too. `settings.js`
fills them by calling `CREATE.renderSettings()`.

What threw was **a curate list cached by 4.1**. That version cached rows from a
label query and they carried no `subs`; 4.1.1 caches project rows that do, and
its drawing reads `t.subs.length`. One undefined array, in a cache that exists
only to save a network call, took out an entire tab — on every install that had
opened that tab once, which is every install that had seen the feature.

`normalise()` now rebuilds the curate cache from its known keys, which is what
its own comment had claimed since 4.1: every field read through a default, every
array proved to be one, subtasks lifted recursively, and a group the shape
cannot account for dropped rather than drawn half-built. Nothing is lost by
dropping a cache — the next visit fetches it again, which costs one call and
cannot fail.

### And behind it, the setting really was empty

`js/create.js`. `create.curate` was `{ label, maxAgeMin }` for the one version
4.1.0 was current. A Config override is stored **whole-branch** (ROOT.md §3), so
an install that had ever touched that field kept the old object — and `project`
read as undefined the moment 4.1.1 renamed the key. No chip on the strip, a
blank field in Settings.

The branch is read through the shipped defaults now,
`Object.assign({}, Config.defaults(path), Config.get(path))` — the same merge
`log.meds`, `log.medsOn` and `plan.formFields` have always used, and safe for
the same reason: a fixed set of keys with no deletion to express, so a missing
one means "not answered" rather than "gone". The stale `label` is dropped
rather than carried: a label is not a project, so there is nothing in the old
value that answers the new question.

**Decision worth naming:** the fallback is on the key being **absent**, never on
its value being falsy. A project that is present and empty is a *choice* —
"blank switches the tab off", which the settings row says — and the first
version of this fix took that choice away by restoring the default whenever the
string was empty. The two blanks are not the same thing, and the harness now
holds both.

### A filter that no longer exists falls back

`js/create.js`. This is what turned a config mismatch into a *blank screen*
rather than a missing chip. The strip had dropped `curate`, but the shelf's own
filter still said `curate` — so `renderHome()` hid every shelf box, showed the
curate list, and there was nothing left on the page to tap. `areaSel()` already
had that fallback for an area deleted in the editor and did not have it for
this. Anything that can be *selected* has to be able to stop existing.

### And the field says what it goes back to

`js/create.js`. The project input carries the shipped value as its placeholder,
so an empty one reads as a choice rather than as something missing.

### The manifest

`ROOT.md` — three §6 notes (a throw at boot deletes the whole app; a cache is
the part of a record whose shape changes most and is checked least;
`Config.get()` on a branch whose shape changed hands back the old shape), §7's
harness count, and the 4.1.2 changelog entry.

## Verification

`cd test && node harness.mjs` — **896 checks, all green** (885 at 4.1.1), 11
new. Five of them boot a whole second window holding the exact state that broke,
which is the only way to catch a failure that happens *during* boot:

- an install with 4.1's cached row shape — the module survives, the cached list
  is lifted and drawn rather than dropped, every row it lifts has the arrays the
  drawing walks, and the settings panel fills because the module that fills it
  exists
- an install with a cached group too broken to lift — dropped, module alive
- an install with 4.1's `create.curate` override — the chip is back, the field
  shows `02 | curate`, and the stale `label` is not kept
- an install that blanked the project on purpose — still switched off
- a shelf left on a filter that has since gone — falls back to the shelf

`bootWith()` grew a third argument for it: arbitrary localStorage keys, so an
install can be described completely before the page runs.
