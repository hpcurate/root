## What was done

### CAL — an eighth app

A new tab, built to the "add an app tab" recipe in ROOT.md §7: `js/cal.js`,
`css/cal.css` scoped to `.ns-cal`, a `<section class="view ns-cal">` whose
`#s-home` starts with the shared `.h-top` band, a `tab-cal` sprite symbol, a nav
button, a settings panel, and its rows in `PANELS` / `CATS` / `SEG_NAMES` /
`APP_NAMES` / `APP_HINTS` / `RENDERERS` / `GROUPS` and `search.js`.

One screen, no sub-screens: a horizontal strip of the days that have been
planned, then the chosen day as proportional blocks — an hour is drawn an hour
tall. Time gutter on the left, a coloured edge per row, the task name and its
slot and project underneath.

### The day gets kept instead of thrown away

Everything needed to draw a calendar was already being computed at export time
and discarded the moment the Todoist task was written. `calendarDay()` in
`plan.js` now captures it and `doExport()` hands it to `CAL.write()` — **after**
the Todoist call succeeds, so a drawn day is always a scheduled day. Stored in
`cal_days_v1`, one entry per ISO day, re-export replacing whole.

Three design decisions, all recorded in ROOT.md §6 and §9:

- **The whole template is stored, not the exported lines.** `mode: blocks`
  sends only the assigned slots, but the day still has the shape the template
  gives it. Unclaimed slots are stored as `idle`, template events as `fixed`,
  and each kind can be switched off.
- **A stored day is a record, not a live query.** Every row carries its own
  clock time, calendar name and colour, so CAL never reads `plan.types` and a
  project recoloured later cannot repaint a day already planned.
- **Written on success only.** A day drawn for a failed export would be a day
  that is not actually scheduled.

### Colours

Task rows use the exact value PLAN paints its own project tile with
(`labelHue(label, key) || resolveColor(key)`), so the two views agree rather
than merely resembling each other. The template hours around them are coloured
by the calendar they sit on, from a new editable `cal.eventColors` branch, with
`*` as the fallback.

### Settings

Six dials on a `cal` panel: hour height, show the template, show unclaimed
slots, show calendar names, days ahead, keep behind. Plus a stored-days status
line, a clear button routed through `Shell.confirm()`, and `cal.eventColors` /
`cal.idleLabel` as editable content at the end of the panel.

### The trap underneath: a new app does not reach an existing install

`Prefs.apps` is stored whole and replaces the default whole — the same rule
Config uses for a branch. Adding `'cal'` to `Prefs.APPS` therefore gave it a tab
on a fresh install and **nothing at all** on any install that had ever opened
the layout panel, which is every install that has been used. CAL would have
shipped invisible on the actual phone this is for.

`Prefs.appsSeen` now records every app an install has been offered. An app in
`APPS` it has never seen is new and goes in, in its shipped position; an app
missing from `apps` but present in `appsSeen` was switched off deliberately and
stays off. It persists immediately, or switching the new tab back off would be
undone on the next boot.

### Consistency

Everything the "don't touch" line asked for: no literal radii, borders or
padding in `cal.css` (all `var(--r*)`, `var(--bw)`, `calc(… * var(--dens))`),
`text-transform:var(--caps)` on every label, the day strip carrying its own
`touch-action:pan-x pan-y` because it scrolls sideways inside `#track`, no
`position:fixed` anywhere in the slide, one delegated `data-act` listener rather
than inline handlers, and `Shell.confirm()` instead of a bare `confirm()`.

## Verification

`cd root/test && node harness.mjs` — **366 checks, 0 failures**, 38 of them new.

Four existing checks were updated rather than worked around: they assert the tab
list by name and count, which legitimately grows from eight to nine. Two more
that iterate a hardcoded app list (the band-shape rule and the "no app sheet
sets its own `.h-top`" rule) had `cal` added so CAL is actually covered by them.

New coverage: CAL reaching for nothing; the export writing the day under the day
it is for; the whole template stored (2 task / 4 idle / 14 fixed); clock times
resolved from the one start; a task's colour equalling its PLAN tile's; a
recoloured project repainting the tile but not the stored day; heights (30 min →
28px, 90 min → 84px, and the hour dial changing both); the strip offering today
with nothing on it; each dial changing the drawing; the empty state naming the
dial responsible; a failed export writing no day; re-export replacing rather
than merging; the keep window sweeping behind and never ahead; search finding a
planned task by name; `cal_days_v1` filed under CAL in the storage report.

The migration is proved by booting a **second jsdom window** with prefs already
in localStorage — the only way to run `Prefs.load()` twice — once as an install
from before CAL (gains the tab in shipped position; apps it had switched off
stay off; `appsSeen` is written) and once as an install that had already been
offered CAL and turned it down (stays off).
