## What was done

### LOG — the day number moves here (tasks 3 and 6)

One change answers both tasks, because they are one mistake.

2.24.0 put the day number on DO, at the right end of the wordmark's row. That
row also holds the daily/media/other strip, which is `flex:0 1 auto` and gives
up width before anything else does — so the number took roughly 73px the strip
needed and pushed it into scrolling on a phone. That is task 6, and it has no
fix other than taking the number back off that row.

It was also the wrong home on its own terms. On DO the number changes at
midnight and at no other time, so the roll — the entire reason for drawing it at
wordmark size — was something you would see once a day and only if you were
looking at the screen when it happened. LOG steps through days with the arrows
directly above its wordmark, so the number changes whenever they are used and
the roll says which way you went. `paintDayNum()` moved from `do.js` to
`log.js`, keyed off LOG's selected date rather than today, and is called from
`refreshHome()` so every step, every reset and every jump repaints it.

Colour, as asked: `var(--tx)`, the title's own, rather than `var(--mu)`. It is
the second half of that line, not a caption beside it.

### DAY — a day can be started when PLAN never sent one (task 2)

DAY could only ever draw a day PLAN had exported, so a morning with nothing
planned offered one route: leave for PLAN, queue tasks, send them. That is the
right route when there is something to send. It is the wrong one when the blocks
are already on DO — labelled @b1 / @b2 in Todoist, fetched, sitting there — and
the only thing missing is a day-shape to drop them into.

The empty card now carries **schedule from do**, which builds that shape and
opens the slot panel in one tap. Stopping at a grid of `free` rows would have
been stopping one tap short of the point.

**§9 was not bent to do it.** Its rule is that CAL never resolves
`plan.dayTemplates` — the moment it could, there would be two answers to "what
is a normal day" free to drift apart. So:

- `PLAN.blankDay(iso, name, start)` resolves the template, exactly as an export
  does, and returns a record with every slot row `idle` and every template row
  `fixed`. `resolved()` gained an optional start-minutes argument so it can do
  this without touching the export form's state.
- `CAL.write()` is still the only way into the store.
- A harness check now asserts `cal.js` reads no `plan.*` config at all.

What *is* different from an export is that nothing was sent: no Todoist task, no
22:00 agent, no Google. §9's other rule is that DAY never claims a day that was
not actually scheduled, so the record is marked `localOnly` and the head says
**not sent** — permanently, and ahead of `edited`, because it is the larger of
the two claims. A real export for the same date replaces the record whole and
the marker goes with it, which is right: that day *is* sent.

**Decision made on Hugo's behalf:** the reading of the task. "create schedule
from do option also appears when no schedule for the day" could be a bug report
or a request; it cannot be the former, because the option does not currently
appear on an empty day at all, so it is the latter.

### DO — the settings control had no styling (task 4)

2.24.0 wrote `.opts > .opt` for the full/minimal choice. The app's shape for a
choice is `.opt-set > .lbl` then `.chips > .chip` — what `chips()` generates for
the three built panels and what every static panel writes by hand. No stylesheet
has ever contained `.opts` or `.opt`, so the control rendered as two unstyled
buttons. Corrected to the real classes; `syncStatic()` already handles a
`data-val` chip generically, so nothing else changed.

### PLAN — the animation (task 5)

Two things, both named in the task.

**The rule under the project title popped in.** 2.24.0 made it an `::after` on
`.proj-head`, and `el.animate()` cannot touch a pseudo-element — so while every
real element around it was held at opacity 0 by the reveal wave, the rule
appeared on the first frame. It is a real `<span class="ph-rule">` now, a direct
child of the tile (not of `.proj-head`, which holds the movers and is skipped),
absolutely placed so it spans the tile without joining a flex row laid out for
two. It comes down with the section rows, in their stagger — which is what "like
how the sections appear" asks for, because it is now literally the same
animation.

**The title resize was too slow.** The move owned `.58` of the flip budget —
near 400ms at the shipped `--t-flip`. The name growing from 13px to 24px is the
one part of this gesture where the *scale* is what the eye is on rather than the
travel, and a slow scale reads as text struggling to settle where a slow
translate would read as weight. It is `.34` now: the name arrives while the eye
is still following it, the reveal starts sooner, and the whole gesture is
shorter as well as quicker at the front. The harness check that pinned `.58`
literally was rewritten to assert what it was actually guarding — that `travels`
gates the move — plus a new one that the move stays under half the budget.

### The blur (task 1) — the other half of the arithmetic

2.24.0 diagnosed the band's vertical metrics as fractional and snapped the
wordmark with `--title-px`. The blur stayed. The diagnosis was right and the fix
was half of it: **the band has two fractional inputs and the wordmark is only
one.**

The other is the status-bar inset. A notched iPhone reports
`env(safe-area-inset-top)` as 47.33px, and that number lands in the band's
`padding-top` *and* its `min-height` — so with `justify-content:flex-end` every
row inside it was still being pushed to a third of a pixel, and the smallest
text in the band was still being resampled rather than drawn. That is the same
defect, in the term that was overlooked.

`--sat` is the inset snapped with `round(up, …)` — up and never down, because it
is clearance from a physical notch and a header that ends a fraction of a pixel
high is a header with the system clock sitting on it. All thirteen uses across
seven stylesheets now measure from it, so the sub-screen sticky headers (`.hd`,
which is literally what the original task called "the sticky title") get it too,
not only the home band.

## Deferred

What shipped is a real remaining fractional term in the defect already
diagnosed, found by reading the source. It is not a confirmation that the blur
is gone, and this is the second attempt at it, so the task should not be closed
by the person who cannot see the screen.

Three things were not available this session: the image attached to the task is
not reachable through the Todoist API (no comments, no `fileAttachment`), the
browser extension would not connect, and jsdom cannot render a blur. If it
persists, the two remaining candidates are:

1. **`apple-mobile-web-app-status-bar-style: black-translucent` with
   `viewport-fit=cover`.** In standalone on iOS this lets the system composite
   its own translucent bar over the top strip of the page. Changing it to
   `black` would end that, at the cost of the app no longer running edge-to-edge
   under the status bar — a trade-off that is Hugo's to make, not one to make
   for him.
2. **`html{zoom:var(--ui-scale)}`**, if Interface scale has been moved off 1.0.
   The steps are 0.05, so most values put the whole layout on fractional device
   pixels regardless of what the CSS rounds.

The image, or a note saying which of these is in play, settles it in one round.

Everything else in the batch is delivered.
