## What was done

### DO — the media tab (task 3)

2.8 drew media as the block tiles: three across, 64px boxes. That is the right
shape for a block — a word standing for an hour of work — and the wrong one for
a **title**, because titles are long. Three-across at 11px meant four wrapped
lines or an ellipsis on anything past "Dune", so the tab stopped being readable
at exactly the length a backlog reaches.

It is one row per title now (`.md-row`): the label's colour as a rail down the
left edge, the name at two lines before it clips, the kind and the second label
as a meta line under it, the tick on the right where every tickable row in ROOT
keeps it.

Four features came with it, **all drawn from data that was already being fetched
and thrown away** — this is why "add features" did not need new API calls:

- **kind chips**, one per label that has something on it plus "all", each
  carrying its open count. "What films have I got" was a scroll; it is a tap.
- **find**, a substring match on the title. Only once the list passes eight
  items — below that it is furniture.
- **sort**: by kind (grouped, the shipped order), a → z, or by priority.
  Priority has been fetched from Todoist since 2.8 and was shown nowhere.
- **surprise me**, which picks one open title at random from whatever is
  filtered, names it and lights its row. It is the honest answer to what a
  watchlist is for: the problem with forty films is never finding one, it is
  choosing one. It shows the pick rather than acting on it — closing it is still
  the same tick as any other row.

The kind and the sort persist in `td` (`mediaKind`, `mediaSort`); the find box
does not, because a half-typed query two hours old only looks like a broken
list. A stored kind whose label has since been deleted from Config falls back to
"all" rather than hiding the list behind a chip that is no longer drawn. Typing
repaints the rows only (`renderMediaList`), never the head — re-rendering the
whole section on each keystroke would take the focus and the caret with it.

**Decision made on Hugo's behalf:** which features. The task said "add
features" and the clarification said it was Claude's call, so the four above
were chosen on one rule — anything that needed data ROOT was not already
holding was out of scope.

### CAL — deleting a row (task 9)

A day arrives from PLAN whole, and correcting one meant re-exporting it. Rows
can now be deleted, and because there are exactly two honest things to do with
the hour it leaves, it asks rather than choosing:

- **close the gap** — every row after it moves earlier by its duration. The day
  is genuinely shorter and you finish sooner.
- **leave it free** — the row becomes an unclaimed slot and the rest of the day
  stays where it was planned. More often right than it sounds: a train at six is
  still at six whether or not the morning emptied out.

Either way the day is marked `localEdit`, the same as filling it from DO — it no
longer matches what was sent, and §9's rule is that the day says so. An idle row
has no delete: there is nothing in it to remove.

This is the app's first three-answer question, so `Shell.ask` gained an optional
`alt` button, settling as the string `'alt'` so a two-button caller can never
see it by accident, and the action row stacks when there are three — three verbs
across a phone width leaves each of them two words. The delete is a `role=button`
span rather than a nested `<button>` (the row itself is the tick, and a button
inside a button is invalid and does not reliably take the tap), and its click is
stopped so deleting a row does not also tick it.

**Decision made on Hugo's behalf:** the task's "save time" / "no" was read as
close-the-gap / leave-the-hour-free, and the second is implemented by turning the
row into CAL's existing `idle` kind rather than by inventing a new one — an idle
row already means "this hour, nothing in it", which is exactly true of both.

### CAL — the wake-up time moves the day (task 10)

`CAL.setWake(iso, 'HH:MM')`, called by LOG when the morning form is saved. The
whole day shifts by `wake − start`: it keeps its shape, which is the thing this
app draws, and only its position on the clock changes. `rec.wakeShift` records
what has already been applied, which makes it idempotent and reversible —
correcting 08:10 to 07:50 moves the day by twenty minutes, not by another two
hours and ten, and clearing the field puts it back where PLAN wrote it. LOG only
says what the time was; every piece of the arithmetic is CAL's.

**Decision made on Hugo's behalf:** it is on by default, since the task asked
for the behaviour, but it is a dial (settings → apps → cal) because a silent
whole-day shift is a large thing to do without a way to stop it. The toast says
when it happens.

### CAL — colourful events (task 8)

Two switches, exactly as asked: `calColorBlocks` for the task rows (the b1a /
b2b slots) and `calColorOther` for the template hours. A 12% wash over the
surface the row already has, not a fill — a row filled with its colour is a row
you read the colour of instead of the words. Both on is a rainbow, which is why
it is two dials. An unclaimed slot is never lit; a done row stands its wash down
with everything else on it.

### CAL — the head (task 1)

The meta was one run of text with `·` typed into it, so a line could break at any
space, and did in the worst place: "5 tasks" and "3 done" came apart across two
lines, a number stranded above its noun. Each fact is its own inline element now
with the separator drawn by CSS, so a break can only fall *between* facts. The
head also stacks — meta on one row, actions on the next — because on a phone the
facts wanted the full width and `schedule from do` was taking it. That button is
`+ do`: same accent, same job, a quarter of the length.

### CAL — inert while scrolling (task 7)

2.22.3 took the press *wash* off anything scrolled under a finger and 2.23
swallowed the click that ends a drag; both are about the tap that follows. The
day is the one screen where that is not enough, because its rows are as tall as
the hours they stand for, so a scroll down a full day is a finger crossing five
or six live controls. For the length of the gesture the day is a picture:
`pointer-events:none` on `.cal-day` and `.cal-head` under `[data-scrolling]`.
The scroll container is the ancestor and keeps its own pointer events, so the
scroll itself is untouched — this only removes the rows as targets.

### Shell — the blurred title (task 2)

Two causes, both fixed.

1. **Arithmetic.** Four of the five title sizes multiply out to a fraction
   (54 × .72 = 38.88, × .86 = 46.44, × 1.16 = 62.64, × 1.34 = 72.36), and the
   band is `justify-content:flex-end`, so that fraction became the offset every
   row inside it was pushed down by. Text landing on a half pixel is resampled
   rather than drawn — and it showed first on the smallest text in the band, the
   date line at the top, which is why the bug read as "the *top* of the title is
   blurred" rather than "the title is blurred". `--title-px` is the wordmark's
   size snapped with `round()`; the band's `min-height` and the wordmark's
   `font-size` are both measured in it. Behind `@supports`, with the unrounded
   value as the fallback.
2. **A held animation.** `.morph` was added on every tab change and never taken
   off, so the title's `both`-filled slide stayed applied for the life of the
   session — which keeps the element on its own compositing layer, where text is
   drawn with grayscale antialiasing instead of subpixel. It now comes off with
   `.leaving`, on the same 900ms timer.

### DO — the date opposite the wordmark (task 6)

The day of the month at the right end of the `DO.` row, cut from the same family
and weight at the same size (`--title-px`, so it follows the Title size dial and
snaps with it) and muted — the wordmark is what the row *is*, the number is what
it is *about*. When the day changes the old number leaves upward and the new one
arrives from below, both clipped by a one-digit-tall box, so it reads as one
number moving forward. `tabular-nums`, so 9 → 10 does not shift the ones column.
It also travels with the title on a tab change, holds still when the track does,
and is off under reduced motion. `aria-hidden`, because the date line above it
already says the date in words.

### DO — minimal cards and hide-when-done (task 5)

`doCardStyle: full | minimal` and `doHideDone`. Minimal is the name and the ratio
on one row, no bar, one column — about a third of the height, so a tab with six
routines is a screen rather than a scroll. What is dropped is only the *drawing*
of the progress; the ratio is the same number the bar was showing. Hiding a
finished routine never touches its state, so switching the dial back off brings
the card back with its ticks. The travel card follows the same rules — it is a
card on that grid like any other. A tab with nothing left says "all done" and
where to get the cards back, rather than leaving a hole where the grid was.

### Shell — the hints switch (task 4)

Settings → behaviour → "Explain the controls". ROOT has no tooltips in the
hover sense; what it has is explanatory text, in two shapes — the paragraph over
a section (`.data-warn` / `.set-note`) and the grey line under a control (a
`<small>` in a switch's label, an `<em>` in a slider's). Those are what the task
is about, and they go off together through one attribute on `<html>`, like the
press wash and the chrome blur, so it reaches every hint at once including any
written later. Never hidden: a control's own name, a section heading, and the
home menu's sub-labels, which say what is *inside* a category rather than
explaining it — losing those is losing the map, not the commentary.

### PLAN — projects and sections (task 11)

The vaguest task in the batch, so what was changed is the three things that were
concretely wrong rather than a restyling:

- **Opening a project cleared the grid of every other one.** The way to the next
  project was back out through the one you were in: close, find, open, with the
  grid rebuilt twice for what is one thought. The others are a strip of chips
  under the open header now, each with its queued count, and one tap moves
  between them with the existing FLIP carrying the section rows out and the new
  ones in. They are `.proj-jump`, deliberately not `.proj-tile` — exactly one
  full project box is open at a time and the rest of the file relies on it.
- **Three section rows each washed in the project's colour read as three
  identical slabs**, with the name — the only thing that differs between them —
  competing with all of it. The colour is a rail down the left edge now (CAL's
  device, and the new media rows'), the surface is the app's ordinary one, and
  the name is the loudest thing in the row.
- **A row never said what was already in it.** Each now carries the count of
  tasks queued into that section, so "where did the other three go" is
  answerable without opening anything.
- The open header keeps a rule in the project's colour under its name, so
  opening a project no longer drains the colour off the screen.

**Decision made on Hugo's behalf:** everything about this one. "Make it feel
better, smooth" does not say what to change, so the changes were chosen by
looking for things that are *wrong* rather than things that are unfashionable —
a navigation dead-end, a colour treatment that flattens the rows it is meant to
distinguish, and information the screen had and did not show. If this is not
what he meant, it is the task to re-file with more detail.

### Found on the way

The app panels are static markup in `index.html`, and their `data-pref` switches
were written with the shipped default on them and then never painted again — so
CAL's three had been showing the default rather than the setting since they
shipped, and flipping one moved the stored value without moving the dot.
`syncStatic()` paints a static panel from Prefs after it renders. It is scoped
away from look / layout / behave, which rebuild their own markup and where two
dials (`radius`, `border`) default to `null` meaning "leave it to the theme" —
painting those this way would have put NaN where the readout says `auto`.
